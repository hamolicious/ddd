Plugin Protocols & Wiring

Today a plugin reaches another plugin by its id, and the shape of what passes between them lives in a file third parties are told to copy. This plan makes every exchange a named, versioned protocol, declares each one as a port in the manifest, and turns who-feeds-whom into wiring you can see and edit in a graph.

§1 · Why

Agreement today is by convention

The kernel is sound: deterministic activation, contained failures, declared-dependents-only services. What breaks down at ecosystem scale is how plugins agree with each other. Each of these is from the current tree.

"dependencies": { "indexer": "^1.0" }

Dependencies name a plugin, not a capability

graph and fm-autocomplete require the plugin called indexer. A better index has to take that exact id, and only one can be installed. Two indexes side by side is impossible to express.

_shared/points.ts · 838 lines

The contracts are a private file

Twenty-five point shapes live in one base-distribution source file whose header tells a third party to "copy the type from here, or simply pass an object with the right fields".

commands: in 9 base manifests, 0 service reads

A dependency means different things

Nine base plugins depend on commands and none reads its service; the edge only says "I contribute commands". Meanwhile header hosts navbar.item and none of the six plugins contributing to it declares it.

"x-defines": [ … ] · informational

Nothing declares what a plugin feeds

x-defines is not tied to runtime, and there is no counterpart for contributions. A misspelled point name buffers forever without a diagnostic.

17 shapes with order?: number

Order is a bidding war

Where a panel or navbar item lands depends on the number each plugin picked for itself: 0, 10, 900, 1000. To go before someone, you undercut their number. No one can see the whole sequence, and the owner of the sidebar can't set it.

kernel.events · "unfiled"

Reverse relationships go untyped

folders tells doc-list where unfiled documents go. The dependency would have been a cycle, so it became an untyped event that no manifest mentions.

§2 · The model

Protocols, ports and wires

A protocol is a versioned contract with an id such as lm/workspace-index@1.2.0. A port is one named place on a plugin where it provides or consumes a protocol. A wire connects a provided port to a consumed port, and the graph only allows it when the types fit: every key the consumer requires must be there with a matching type, and extra keys are fine (§6b). Plugins name ports and protocols. They never name each other.

§3 · Protocol packages

A contract ships on its own

A protocol is a small package with no runtime code of its own besides a validator. It ships inside the plugin that owns it, for example lm/workspace-index inside indexer. On install, the server takes it into its protocol registry, where it stays even if that plugin is unplugged or replaced, so a replacement can speak it too. The kernel still knows no domain: it learns the kind and the shape from the package, never what a navbar is.

Layout

  protocol.json       # generated: id, version, kind, owner, shape
  index.d.ts          # generated from shape.mjs
  shape.mjs           # the one authored source: s.object({…})
  README.md           # semantics: what a provider promises
  conformance.mjs     # optional: tests any provider runs

RuleWhy
Protocol ids are <publisher>/<name>. lm/ is reserved for the base distribution. On each server, the first installed package to use a namespace owns it. Plugin ids keep today's rule (no /).Two authors can both write a "tasks" protocol without colliding.
Semver: removing a method or making a field required is a major. Adding an optional field or a method is a minor.The same rule KERNEL-API.md already applies to @kernel.
The server stores protocols by id@version with a content hash. A second package bundling the same id@version must be byte-identical, or the install is refused.No two plugins can disagree about what lm/route@1.0.0 means.
Types are served at /protocols/<id>/<version>/index.d.ts, like /kernel.d.ts.An outside author compiles against what the server actually has, without copying files.
The shape is plain JSON in the s.* vocabulary: string, number, boolean, func, promise, component, any, literal, union, array, record, object, optional. The s.* builders gain a toJSON(); promise is new.The server and the graph can type-check a wire without running any plugin code.
Only shape.mjs is written by hand. protocol.json and index.d.ts are generated from it, and CI fails when the checked-in output is stale.One source, so the five hand-written RouterService copies can't happen again.
A provider that says X@v implements all of X@v. Everything it offers or serves is checked against that version's full shape; a failure fails the plugin. Partial support is an older version, or members the protocol marks optional.A version number means the same thing for every provider.
Duplicate rules are data: "key": "id" names the field that must be unique on a host. The lower seat wins a duplicate.Today definePoint({ key: fn }) takes a function, which can't be serialised, and "first wins" depends on activation timing.
A protocol package ships in its plugin's protocols/ folder: in the install zip allowlist, in build-plugins.mjs, package-plugin.mjs and compose-plugins.mjs, and registered when the server scans base plugins as well as on install. The registry travels in the plugin list, so clients can still validate after the owner is gone. In development a plugin may overwrite its own protocol without a version bump.Today the zip allowlist and the build copy only manifest.json, frontend/** and the declared wasm.

                "needs": ["navigate", "query"] },
    "shell":  { "protocol": "lm/shell@^1.0",
                "needs": ["layout", "toggleAltbar"] }
  },
  "provides": {
    "view":     { "protocol": "lm/main.view@1.0.0" },
    "panel":    { "protocol": "lm/altbar.panel@1.0.0" },
    "route":    { "protocol": "lm/router.route@1.0.0" },
    "commands": { "protocol": "lm/commands.command@1.0.0" },
    "keys":     { "protocol": "lm/keybindings.default@1.0.0" },
    "nav":      { "protocol": "lm/navbar.item@1.0.0" }
  }
}

A consumed port takes a semver range; a provided port states the exact version it implements. needs narrows a consumed port to the keys it actually uses, and the type check only asks for those (§6b). A needs key the protocol doesn't have is refused at install. "optional": true on a consumed service port covers the review's P2 (optional dependencies). A host port looks the same as any consumed port: the protocol's kind: "slot" is what makes it many-to-one. A host that shows exactly one contributor adds "seats": 1. There are no ordering numbers anywhere in the manifest, because order belongs to the wiring (§6a).

§5 · Runtime API

kernel.ports, addressed by your own port names

export default function activate(kernel: Kernel) {
  // service: whatever the wiring bound to "index"
  const index = kernel.ports.use<WorkspaceIndex>("index");

  // slot items: validated against the protocol's shape
  kernel.ports.offer("view", { id: "graph", component: GraphView });
  kernel.ports.offer("commands", [openGraph, focusNode]);

  // host side: a live list of what is wired in, in seat order
  const items = kernel.ports.collect<NavbarItem>("items");
  items.subscribe(render);

  // events
  kernel.ports.emit("unfiled", { path: "inbox" });
  kernel.ports.on("unfiled", (m) => …);

  // providing a service
  kernel.ports.serve("index", api);
}

Port names are local. graph says use("index"), not require("indexer"). Which plugin answers is a wiring decision made outside the plugin.

Undeclared ports throw, keeping the current ContractViolationError discipline from runtime/services.ts.

needs is enforced. ports.use() returns a handle limited to the declared keys. Reading any other key throws ContractViolationError, in development and production alike.

Kernel types become generic: ports.use is typed by the protocol package's index.d.ts, pulled in at build time.

Shims are temporary. During the migration, extensions.contribute("navbar.item", x) becomes offer on an implicit port speaking lm/navbar.item@1, and services.require("indexer") becomes use on an implicit port bound to that plugin. Once the base plugins and examples are ported, the shims, dependencies and x-defines are removed and @kernel 2.0 has only ports. A 1.x plugin then no longer loads.

§6 · Resolution rules

Auto-wire by default, store only the overrides

Most installs never open the graph. The resolver wires everything it can, and the wiring file records only the choices a person made. A new plugin therefore joins every compatible host without anyone editing wiring.

One resolver, and boot doesn't need Wasm. It lives in the Rust core as core::wiring. The server runs it natively and puts the resolved result (bindings, seats, activation order, and the same for ?safe=1) in the plugin list, so the loader only reads data and boot still works when the Wasm core fails to load (kernel-init.ts). The wiring editor runs the same code through Wasm for instant previews; without Wasm it is read-only. corpus/wiring.json pins both, like corpus/splices.json.

Applied as a unit. Edits collect in a draft. Apply commits the draft as a new version and every connected client rewires in place (§6c).

Stored beside plugin state. In Mongo next to PluginState, with the last applied version cached on disk, so the plugin list is still served when Mongo is down, as today.

Every change is a version. Apply, rollback, install, upgrade, uninstall, approval and a circuit-breaker trip each write a new version and send the same wiring.applied frame. Uninstall also drops the plugin's entries from order, cut, add and bind.

§6a · Seats

Connection order is seat order

A slot port on a host is multi-seat. The graph draws its seats as overlapping dots running down the node's edge, one per wire, with seat 1 at the top and an open seat at the bottom. The port's row grows to make room. Every new connection takes the open seat, so the order you connect things is the order the host receives them. For a sidebar, that is the order of its panels from top to bottom.

RuleDetail
Connecting takes the open seatA new wire always goes at the end. To move a contributor, cut its wire and connect it again, or use the up/down controls in the seat list.
The order is stored as a listwiring.json keeps order["shell-ui:sidebar"] as the full list of sources, in seat order, from the first edit onwards.
Default seats come from the order hintBefore anyone edits a port, contributors are seated by their order hint, then alphabetically by plugin id. That keeps today's layout, including alt-editor's place among document modes. A plugin added later sits after the seats already listed in order.
Single-seat hosts: "seats": 1For example, shell-ui:header shows one top bar. A new connection goes into the only seat and moves the previous occupant to the bench, which the graph draws as a faded wire. This replaces "lowest order wins".
The host receives seat orderkernel.ports.collect() returns items by seat. When a plugin offers several items on one port, they stay together in the order that plugin offered them.
order?: number becomes a hintIt only sets the default seat. wiring.order always wins over it.
Hosts stop sortingAbout 15 hosts sort by order themselves today (Shell.tsx, header/layout.ts, editor, document-surface/modes.ts, markdown, slash-commands, doc-list search, attachments). They take collect() order instead. router keeps route specificity first and uses seat order only to break ties.

Seat order is the workspace default, set by whoever edits the wiring. A host can still let each user rearrange on top of it, like header's existing "Top bar" ordering setting. That personal order starts from the seat order and never feeds back into the wiring.

§6b · Type checking

A wire exists only if the types fit

Every port carries a shape, and the graph refuses a connection before it exists: while you drag, ports that don't fit fade and say why. The check is structural. The consumer's shape is the requirement and the provider's shape is the offer.

Consumer needsProvider offersResult
{ id: string, title: string }{ id: string, title: string, icon: any }fits Extra keys are ignored.
{ id: string, search: func }{ id: string, query: func }refused Missing required search.
{ id: string }{ id: number }refused id is number, needs string.

Consumers say what they use. Five base plugins each declare their own RouterService interface today, each a different slice: changes uses navigate, graph uses navigate and query, settings uses navigate and url. MarkdownApi is declared twice the same way. needs writes that slice into the manifest, so a smaller router can serve changes without implementing url.

The same provider can fit one consumer and not another. graph reads five members of the index and fm-autocomplete reads three different ones. In the prototype, acme-fuzzy-index implements lm/workspace-index@1.0.0, before fmFields and fmValues existed (an example history). It serves graph (^1.0) and is refused for fm-autocomplete (^1.1).

Shape decides what is allowed; protocol decides what is automatic. markdown.codeBlock and markdown.attachment have the same shape, and a main view fits the overlay layer. Auto-wiring therefore needs the same protocol id and a version in range. A manual "by shape" wire across protocols is allowed for slots only, after a confirm naming both protocols. Services are mostly func, so a shape match says little there; they and events need the same protocol id, and adapters cover the rest.

Semver still matters for meaning. SectionLineEdit's value: null changed meaning in 1.1.0 without changing shape (KERNEL-API.md). A type check can't see that, and a major version bump can. A "by shape" wire says a person has vouched for the meaning.

Runtime still validates. A declared shape can be wrong. Each item a provider offers is checked against the shape of every consumer it is wired to, and a failure is reported against the provider.

§6c · Drafts, apply and hot-plugging

Nothing changes until you press Apply

Every edit in the graph goes into a draft: a wire, a seat, a pin or unplugging a plugin. The draft is stored on the server with the live version it started from, so it survives a reload and other admins can see it. The graph draws the draft over live wiring. New wires are bold, removed wires are red ghosts, and the side panel lists the consequences before anything runs. Apply commits the draft as the next version and every connected client switches to it, in place.

What unplugging a plugin does
Its wiresDisappear from the draft. Its seats stay in order, so plugging it back in returns it to the same seat.
Its dependentsA plugin that required a service only this one provided stops too. The draft names them first, for example "unplugging router also stops 7 others".
Its stateUnplug is disable. PluginState stays the gate the server, the circuit breaker and backend halves use, and unplugged mirrors it both ways, so unplugging also stops a backend half. Its settings section and any documents it created stay.
Drafts
Kept in the editorThe draft lives in the admin's browser. Apply sends it with the live version it started from.
Live moved onThe server refuses a draft whose base isn't the live version. The editor loads the new live wiring, re-applies the draft's edits on top, and shows what changed before you Apply again.
RollbackEvery applied version is kept on the server. Rolling back loads an old version as a draft, and it goes through Apply like any other edit.
What Apply runs

  1. Validate

    The server refuses a draft whose base isn't the live version, then runs the resolver on it. A draft that adds errors, such as a plugin that won't activate, needs an explicit confirm. So does a draft that would stop the running wiring editor.

  2. Commit

    Wiring version N+1 is written atomically, N goes into history, PluginState is updated for anything plugged or unplugged, and the change is audited as wiring.apply (or wiring.rollback).

  3. Broadcast

    A wiring.applied frame goes out on the sync socket, the channel plugin.event already uses. A client that is offline gets the new version from bootstrap when it reconnects.

  4. Hot-apply on every client

    Each client compares the version it runs with N+1 and changes only the difference. First it stops what goes away, in reverse activation order. Then it restarts every plugin whose service wires changed, plus everything that depends on those through services, and updates hosts' seats and event listeners with no restart. Last it starts what arrives, in activation order. A frame that arrives while boot or another apply is still running waits its turn.

  5. Reload only as a fallback, and only when the user says so

    A client needs a reload in three cases: a plugin the change touches doesn't declare "hot": true, a newly plugged plugin needs a library missing from the page's import map (the map is fixed when the page loads), or a stop throws. It then shows a banner and keeps running its current version until the user chooses to reload, which goes straight to the newest version. The banner is the same one the service-worker update uses (boot/update.ts), not a second prompt. Text is safe either way, because edits already live in the local Yjs document and the outbox.

Service changes restart their consumers. Consumers register callbacks on providers (router.onChange, index.subscribe, shell.subscribeLayout), and no handle can move those to a new provider. So when a service wire changes, the consumer and everything that depends on it through services restart, in activation order. Slots, seats, events and leaf plugins hot-apply in place.

Events can be sticky. An event protocol may declare "sticky": true: a new or restarted listener gets the last value at once. lm/folders.default-location needs it, because folders announces only at activation and a restarted doc-list would otherwise forget the folder (doc-list/index.tsx:40-50).

"hot": true is a promise. A plugin declares that the kernel's retraction plus its own deactivate() leave nothing behind. Without it, any change that touches the plugin falls back to a reload. All base plugins get it in migration step 6. In the prototype, alt-editor doesn't have it, to show the fallback.

Code can't be unloaded. An ES module stays in memory once imported, so an unplugged plugin's module sits there, inert, until the next reload. Plugging a new version imports its new versioned URL. That is harmless, but a session that swaps plugins many times piles up dead modules.

This retires the review's "reload-only" position. PLUGIN-ARCHITECTURE-REVIEW.md said hot activation should wait until every public surface has an explicit disposal contract. The table above is that contract, and half of it exists already.

    §10 · Decisions
    Settled on 2026-09-28
    
  
    
    
    Wire per port, not per item
    A wire and a seat belong to a whole port. A plugin that needs items ordered separately splits them across ports, so the graph and wiring.json stay small.
    
    
    The first install claims a namespace
    On each server, the first installed package to use a namespace such as acme/ owns it. lm/ is reserved from day one. Signed publisher keys come later, noted in dev-docs/todo/PROTOCOL-SIGNING.md.
    
    
    Backend Wasm halves get ports later
    This work is frontend only. The host ABI keeps its own semver, and backend events and routes become protocols in a follow-up.
    
    
    Wiring is per workspace
    Wiring decides what code runs for everyone, like enable and disable. Per-user preferences stay inside plugins, such as header's "Top bar" ordering.
    
    
    Adapters are ordinary plugins
    No special machinery. A plugin that consumes X@1 and provides X@2 is an adapter, and the graph suggests installed ones whenever it reports a version or shape mismatch.
    
    
    Unplug is disable
    PluginState stays the gate for the server, the circuit breaker and backend halves; unplugged mirrors it both ways.
    
    
    Default seats follow the order hint
    Then alphabetical by plugin id. wiring.order overrides it; up/down controls and cut-and-reconnect both edit it.
    
    
    By-shape wires for slots only
    Across protocols, slots can be wired by hand after a confirm naming both protocols. Services and events need the same protocol id.
    
    
    needs is enforced everywhere
    The handle refuses undeclared keys in production too, and a needs key the protocol lacks is refused at install.
    
    
    The layout holds still while you edit
    Columns by dependants are recomputed on load, Apply and Tidy only. Rows still grow for seats, and the boxes below move down.
    
    
    Read-only offline
    When the client is offline, the editor shows the cached live wiring and nothing else: no editing, no drafts, no Apply, no rollback. The controls come back when sync reports the server again.
    
    
    The way back is the bare manager
    Nothing is pinned. ?safe=bare gets an admin-only write path to plug plugins back in and roll back.
    
    
    The editor is its own plugin, in the app's UI
    wiring, not part of admin. The app's tokens and components, no explanatory prose on screen, a full-width graph on desktop and a full-screen graph with a bottom-sheet inspector on phones.
    
    
    A reload fallback asks the user
    Hot applies are silent. A client that needs a reload shows a banner and keeps running its current version until that user chooses to reload. Later versions that can be hot-applied wait behind the banner. The reload goes straight to the newest version.
    
    
    Drafts live in the editor
    Apply sends the base version and the server refuses a mismatch; the editor rebases and shows the difference. History and rollback stay on the server.
    
    
    @kernel 1.2 during migration, 2.0 at the end
    kernel.ports ships as a minor so ported and unported plugins coexist. The last step deletes the old paths and bumps to 2.0.0; 1.x plugins then stop loading.
    
    
    Protocols live in the plugin that owns them
    plugins/base/<id>/protocols/<name>/, installed with that plugin and kept in the server's registry independently of it.
    
    
    Frontend plugins stay curated and full-trust
    Frontend plugins keep running unsandboxed after admin approval, as today, with provenance and review strengthened over time. Protocols don't change the trust boundary, and a sandboxed plugin class is not part of this plan.
